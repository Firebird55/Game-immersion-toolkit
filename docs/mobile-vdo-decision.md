# Native mobile source: decision and evidence

Reviewed 2026-10-23. Implementation plan: [mobile-vdo-plan.md](mobile-vdo-plan.md).

## Transport boundary

The static receiver accepts a frame source. Capture transport owns its connection;
OCR owns at most one acquired frame and releases it after use. The existing
browser preview is wrapped without another peer connection. VDO-specific URL
validation, iframe messaging and image decoding stay in its adapter. A future
native sender can implement the same source methods without changing the reader,
catalog, account integration or calibrated OCR coordinates.

The first VDO adapter uses the official hosted viewer's frame API. This preserves
the viewer's direct or WHEP transport behavior and avoids implementing a second
media receiver. The [SDK transport guide](https://sdk.vdo.ninja/docs/streaming.html)
distinguishes SDK peer viewing from WHEP; a native viewer link is not itself a
WHEP endpoint. No SDK package or new backend is added. Existing dependencies
remain pinned in the lockfile. The external hosted viewer cannot be version-pinned
by this application: its compatibility is a documented external-service risk.

Supported inputs are the official `vdo.ninja` single-stream `view`/`pull` links,
reviewed official `whepplay`/`whep` endpoints, and the known
`meshcast.io/view.html?geo=REGION&id=STREAM` form (or `api` instead of `geo`).
Meshcast's current `view.js` provides the exact latter mapping to
`https://REGION.meshcast.io/STREAM/whep`; its viewer itself lacks the frame API.
Only the reviewed `usw2`, `de1` and `cn1` regions are accepted. Unknown parameters,
credentials or routes are rejected instead of discarded. Accepted direct links
retain their password and signaling parameters in memory.

## Observed frame protocol

The [iframe API guide](https://docs.vdo.ninja/guides/iframe-api-documentation/iframe-api-basics)
describes `getVideoFrame` and callback IDs. Inspection of the currently served
official viewer (`main.js?ver=1092`, `lib.js?ver=14213`) found a more specific wire
format than the guide's base64 description:

```js
// Parent to the exact official iframe origin, selecting one remote stream:
{ getVideoFrame: true, streamID, cib }
// The WHEP viewer selects the observed remote UUID instead of streamID.
// Official viewer reply:
{ action: 'image-frame-capture', value: {
  imageData: /* Blob with image/png type */, imageType: 'png', cib,
  streamID, UUID, videoID
} }
```

The adapter checks the iframe window, exact origin, current session and
callback, image type/size/dimensions and selected stream before accepting pixels.
Only one request and decode is active; late responses cannot escape cancellation
or source replacement. No camera, microphone or display-capture permission is
delegated to the receiving iframe. CSP permits frames only from `https://vdo.ninja`;
the parent does not gain arbitrary external script or media-service access.

A correlated screenshot proves frame access, not continuous capture. In this
initial integration `live` requires observed pixel progress. An unchanged image
eventually becomes `stalled` with wording that also covers a legitimately static
scene. Receiver timestamps measure receipt, not end-to-end latency. Do not infer
P2P-only transport or local-only media from these observations.

If the sender stops while its phone is locked, automatic receiver recovery
reuses the same link with a new session, bounded retry delay and a single iframe.
The receiver retains OCR intent, but no result from the retired session may be
published. Explicit Stop cancels recovery. Restarting the native system broadcast
remains an action on the sender; the receiver then resumes when frames return.
Retries start at one second and increase to a maximum of 30 seconds. A missing
frame request times out after four seconds, with a 15-second startup grace;
30 seconds without pixel progress also replaces a frozen viewer. Identical PNG
replies cannot indefinitely postpone this recovery. A static scene remains
explicitly unconfirmed rather than being presented as a proven network failure.
While OCR owns a frame, the no-progress reconnect is deferred because the
single-frame source cannot acquire another sample. A same-session progress stall
does not cancel that scan. Actual disconnects, session changes, pause and Stop
still invalidate pending results; after release, normal probing/recovery resumes.

## Native assumptions requiring a device test

The [App Store history](https://apps.apple.com/us/app/vdo-ninja/id1607609685)
shows 5.0.108 at review and mentions Meshcast viewer delivery in 5.0.102. The
[native screen guide](https://docs.vdo.ninja/guides/screen-share-your-iphone-ipad)
describes SCREEN, Apple's broadcast picker, and an app-generated viewer link or
configured WHIP destination. Those descriptions do not prove the exact link
generated by a particular installed SCREEN build. Public Flutter source may lag
the binary; unsupported link forms must be rejected clearly rather than reduced
to a guessed stream ID. The installed native app and standard viewer must be
tested before accepting this route on two physical devices.

Start with Balanced in the native app and measure text legibility and stability.
The [quality guide](https://docs.vdo.ninja/guides/improving-quality-of-the-native-app)
lists encoder bounds; receiver query parameters do not override native preset
limits. A stopped broadcast may need manual restart. Desktop WebKit cannot
establish background capture reliability under heavy iOS gameplay.

## Public compatibility review

`lexirise:watch` returned exit 2 on 2026-10-23: public UI bundle hashes changed,
while normalized API documentation and the endpoint list were unchanged. The
review read the public [API reference](https://lexirise.app/api-reference) and
current site bundles, including settings patch merging, per-language translation
selection, word-popup tabs, popup portal/pointer handling, reading aids and
Chinese script choices. The API settings contract still separates global and
per-language values and provides effective translation targets. Existing shared
components consume that contract; this source integration changes none of it.

No account request or write was used in this review. The shared vendor and its
baseline remain unchanged. Existing mock account, reader/Shadow DOM and language
regression checks remain part of validation. This is a compatibility assessment
for the mobile source change, not a claim of pixel parity with the public site.

## Validation record

An authorized native iPhone stream was read through the production adapter:
eight decoded PNG frames at 590 × 1280 were received. Only numerical observations
were retained; no viewer identifier or captured image belongs in this record.
This establishes current native direct-viewer/frame-API compatibility to the
desktop browser used for the probe, not two-iOS gameplay endurance or recovery.

Local automated validation passed: 150 Node tests, with the Windows-only installer
test skipped on macOS; production and static mobile builds; documentation and
public-history audit. `check:changed` selected ten browser scenarios. All passed,
including the native bridge and full real OCR/catalog/reader pipeline in Chromium,
Firefox and WebKit, same-link automatic recovery, stale replies, source switching,
visibility, Chinese text, rotation and zoom. Existing pairing, transcript, reader,
offline/update and OCR-pack scenarios also passed on their supported test engines.
The final selector gate used `CHECK_SPLIT_BROWSER_TESTS=true` because its selected
browser scenarios were run separately. The cross-reviews resolved cancellation
and synchronous lifecycle races; capture regression checks prove each frame
monitor is removed on pause/stop and cannot accumulate across recovery.

The physical sender lock/restart and 60-minute two-iOS tests were deferred by the
tester. They remain unverified. The final PR records packaged-build and hosted
results separately from that physical acceptance. Timing and local
diagnostic output stay under ignored `output/checks`; no viewer link, screenshot
of a real game, account diagnostic or local profile path belongs in a public
artifact. Follow [the physical verification protocol](mobile-capture-verification.md)
before claiming the reported iOS background issue is resolved.
